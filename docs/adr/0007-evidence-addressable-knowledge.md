# ADR-0007 — Knowledge Is Evidence-Addressable

- **Status:** Accepted
- **Date:** 2026-11-22
- **Phase:** 00
- **Related Documents:** [GOVERNANCE.md](../../GOVERNANCE.md) · [Data Classification](../security/data-classification.md)

## Context

Architectural decisions, DAW qualification rules, and code/audio specifications generated by AETHER FORGE must be grounded in verifiable sources rather than unattributed semantic recall.

## Decision

The Knowledge Service implements an **evidence-addressable storage and retrieval architecture**:
1. **Canonical Metadata:** PostgreSQL 16 stores source records, tenant ownership, data classification, SHA-256 content hashes, extraction versions, and deletion tombstones.
2. **Immutable Originals:** S3-compatible object storage holds the immutable raw source artifacts.
3. **Vector Retrieval:** `pgvector` indexes chunk embeddings strictly linked to canonical Postgres source rows.

**Explicit Boundary Rule:** Every retrieval result (`GroundedContext`) must include `sourceId`, `contentHash`, `location`, `classification`, and `extractionVersion`. Any model statement not backed by a valid citation must be explicitly labeled as `model_inference`. Deleted or quarantined sources must immediately cease appearing in retrieval results.

## Alternatives Considered

- **Standalone vector database without relational metadata:** Rejected due to weak transactional guarantees around tenant isolation and deletion propagation.
- **Raw filesystem search only:** Rejected due to poor semantic retrieval across large technical documentation sets.
- **Graph-first database:** Rejected as premature complexity for v1.0 requirements.

## Consequences

- **Positive:** Full provenance from plan assumption back to exact document chunk hash; reliable GDPR/tenant deletion propagation.
- **Negative / Trade-offs:** Requires a disciplined ingestion pipeline with malware/type scanning, chunk hashing, and embedding version migrations.
